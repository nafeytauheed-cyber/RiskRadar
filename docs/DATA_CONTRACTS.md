# Data contracts

Schema 1 requires event_id, equipment_id, lifecycle_id, session_id, sequence, cycle, observed_at, values, units and quality. See `backend/app/platform/contracts.py`. Temperature degC, vibration mm/s, pressure kPa, current A and rpm rpm are explicit. Null values require bad/missing flags. Tenant and received_at are forbidden client fields. Server assigns receipt timestamps after acquiring admission locks. Device keys may only ingest their assigned equipment. Bodies are limited to 16 KiB, including chunked bodies; queues default to 10,000 outstanding events per tenant. Duplicate event IDs with identical normalized payloads return success; conflicts and reused sequence/cycle identities return 409. No success is returned before the transaction commits. Database errors return 503.

Cycles are operating counters, not time units. Labels refer to `(current_cycle, current_cycle+30]`. Rows at/after failure, after intervention, with inadequate follow-up, or ambiguous lifecycle outcomes are excluded. Unknown outcomes are not negatives. Maintenance must create an explicit new lifecycle; restart creates a new session but does not imply repair.

Features sort by cycle/observation/sequence/event ID within one equipment/lifecycle/session. Both observation and arrival cutoffs are enforced. Window: last 10 operating cycles; minimum five valid samples per sensor; causal fill at most two cycles and 24 hours; no interpolation or backward fill. Missing, warmup, stale, imputed and good are separate states. Missing/stale/warmup abstain. Idle freshness is recomputed at query time without mutating historical predictions. Device clocks up to five minutes ahead are accepted; older than year 2000 is rejected. Delays otherwise have no maximum ingestion age; only affected targets within the ten-cycle feature window get revisions. Raw events are preserved.

Live ordering is committed arrival order, with equipment serialization. Late events append revisions to already processed affected predictions. Revisions never rewrite or retrospectively close incidents. Observation time gates current-state advancement; an event at/before the current state's timestamp cannot replace it. Device timestamps and operating counters are assumed monotone within a valid session; stronger cross-event clock diagnostics remain on the roadmap.

Incident policy: two successive eligible probabilities >=0.5 open one incident per equipment. A missing/low reading resets the high streak. Acknowledgement and investigation require an operator; resolution requires a note. Resolution never occurs automatically on missing data. A subsequent pair of high readings can create a new incident (reopening by new ID, preserving prior history). Every transition requires the expected version. Alert-to-failure evaluation matches the earliest warning in the 30-cycle pre-failure window; unmatched warning events are false alerts. Incident-level matching is separately required before policy tuning.

Outbox delivery is at least once, five attempts maximum. A receiver success followed by a sender crash can cause another delivery. The receiver must deduplicate the tenant-qualified Idempotency-Key. No delivery daemon runs unless an operator configures its endpoint.

Updated causal-v2: historical samples older than 24 hours relative to the target are excluded, so idle gaps re-enter warm-up. Within-session sequence, cycle and observed_at order must agree with already persisted neighbors; inconsistent events return 409. Corrected replay uses final arrival visibility but original arrival time for freshness, preventing hindsight alone from making every historical row stale. These two cutoffs are recorded separately. Maintenance outcome API drains existing jobs before opening a new lifecycle, fences old leases and resets processing state. Original lifecycle events remain immutable; late submissions to a retired lifecycle are rejected for explicit offline review.

Late revisions pin the target's original model even if a newer model has since been promoted. The new late observation's own prediction uses the currently promoted model. This prevents a data correction from silently becoming a model comparison. Old artifact/feature versions must remain supported before promotion across feature schemas; causal-v1 is an earlier draft checkpoint, not a supported live deployment format in this branch.
